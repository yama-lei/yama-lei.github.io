第一讲：目标文件格式

程序的转换处理过程：

从预处理到生成.o文件的过程中，一直都是单文件的处理。并且生成的.o文件里面使用的是符号（而非绝对地址） 到了链接的这一步，把多个.o文件合并成为一个可执行文件，所有的符号都替换成为绝对地址。（链接实际上做的就是符号解析和重定位两件事情，确定符号的地址，再把符号替换为地址）

程序的编译与链接过程

从源代码（.c）到可执行文件的转换主要经历四个阶段：预处理、编译、汇编和链接。

I. 编译系统（前三个阶段）
这三个阶段以单个源文件为单位独立处理。

  • 预处理（Preprocessing）
    命令：gcc -E
    输入：hello.c（C 源文件）
    输出：hello.i（文本文件）
    任务：展开 #include 头文件、替换 #define 宏、处理 #if/#else 等条件编译指令，并删除 /* ... */ 注释。

  • 编译（Compilation）
    命令：gcc -S
    输入：hello.i（预处理后的 C 代码）
    输出：hello.s（汇编代码，文本文件）
    任务：进行词法、语法和语义分析，生成与 C 代码等价的汇编指令。对外部函数或变量的引用（如调用其他文件中的函数）在此阶段被表示为符号（Symbol），其具体地址尚未确定。

  • 汇编（Assembly）
    命令：gcc -c
    输入：hello.s（汇编代码）
    输出：hello.o（可重定位目标文件，二进制格式）
    任务：将汇编指令翻译为二进制机器码，生成符号表（记录本文件定义和引用的全局符号）以及重定位信息（标记代码中引用了地址未定符号的位置）。

II. 链接系统（最后一个阶段）
该阶段将多个 .o 文件和库文件合并，解决跨文件引用问题。 链接多个.o文件的时候不是把每一个.o文件的各个section相连起来，而是合并起来，因为内存是分页的，一页占了4096个字节，如果每一个.o文件都有那么多的section，零碎的内存占用很多，可以将其合并起来。（磁盘空间使用不变，节约的是执行文件时的内存空间）把.text段合并成一个大的.text段，.bss and .data段是一样的。

  • 链接（Linking）
    命令：ld（通常由 gcc 自动调用）
    输入：多个 .o 文件（如 main.o、swap.o）
    输出：可执行文件（如 a.out）
    核心任务包括：

    1. 符号解析（Symbol Resolution）
      目标：确保每个被引用的符号有且仅有一个定义。
      过程：链接器遍历所有 .o 文件的符号表，将符号的“引用”与“定义”关联。
      常见错误：

      • undefined reference to 'xxx'：未找到符号 xxx 的定义。
      • multiple definition of 'xxx'：符号 xxx 在多个文件中被定义。

    2. 重定位（Relocation）
      目标：将代码中的符号引用替换为最终的内存地址。
      过程：

      • 合并：将所有 .o 文件中相同节（如 .text、.data）合并为一个聚合节。
      • 分配地址：为合并后的节及每个定义的符号分配运行时虚拟地址。
      • 修改引用：根据 .o 文件中的重定位信息，将代码中对符号的引用（如函数调用、变量访问）替换为上一步分配的确切虚拟地址。 最终生成一个完全链接、可在内存中加载并运行的可执行文件。 在swap.c文件中

实际上，如果在swap.c文件中即便不写extern int buf[] 直接运行的话，只要链接有buf这个数组其实也行。 符号的引用会记录在REL（重定位表，分为.rel.txt和.rel.data）中记录下来再某一个地使用了XX符号，之后替换为地址。

第二讲：符号解析与重定位

符号和符号表

可重定向目标文件里面有一个符号表(.symtab)，定义了在这个模块中定义的符号。 有三种链接器符号：

  • Global symbols：
  • External Symbols：使用了external声明的变量，或者函数签名的声明都是external symbols。
  • Local Symbols：本地符号在编译的时候就已经被解析了，无需在链接中解析。 做符号解析，只看符号名。

符号解析

全局符号有strong，weak和common区分。 全局符号的特性

  • 强符号：函数、.data节中具有特定初始值的全局变量名、.bss节中被初始化为0的全局变量名int a=1;
  • 弱符号 ：绑定属性为WEAK的符号__attribute__((weak)) int weak_var = 100;
  • COMMON符号 ：COMMON伪节中的未初始化全局变量名int a; 函数名，以及有初始化的全局变量名是强符号。在链接当中同名的强符号只能出现一次。

main函数的地址的第一个字节是push ebp！

在有静态链接库的时候如何进行符号解析？ 链接器维护三个集合来完成符号解析：

  • E: 将被合并成可执行文件的所有 .o 文件的集合。
  • U: 当前未解析（引用了但未定义）的符号的集合。
  • D: 当前已定义的符号的集合。 链接器会从左到右依次扫描命令行上的输入文件：
  • 对于每个输入文件f，链接器判断其类型。
  • 如果f是.o文件，则直接将其加入E，并用f的符号表更新U和D：将f中定义的符号加入D，将f中未定义的符号加入U。
  • 如果f是.a文件（静态库），链接器会尝试用库中的成员来解析U中的符号。它会遍历库中的所有成员.o文件，如果某个成员m定义了U中的一个符号，那么就将m加入E中，并用m的符号表来更新U和D。这个过程会重复进行，直到在库中再也找不到可以解析U中符号的新成员为止。
  • 当所有命令行文件都被扫描完毕后，如果U集合不为空，链接器就会报错；否则，它将合并E中的所有文件，生成最终的可执行文件。
  • 这个过程也解释了为什么库文件通常要放在命令行的后面。

重定位

重定位的信息存储在rel.data和rel.text，分别代表了在data段和text段需要重定位的符号。 数组元素为：

可以读取到这一条的重定位信息：

  • 位置在所在段的r_offset偏移位置
  • 重定位的符号在符号表的r_sym位中

什么时候需要重定位？

  • 引用了外部函数（在本地有声明），在call指令的时候，会跳转到目标地址。通常使用PC32的重定位type，并且A的值常常为-4.(重定位的值=S+A-P)
  • 引用了外部变量
  • 引用了本地全局变量

R_386_PC32的重定位

函数符号对应PC32

PC相对寻址的方式是：目的地址=PC+相对地址，在PC32重定位中，需要找到目的符号的地址，那么就需要修改这里的“相对地址部分”（因为在重定位之前，这一部分的数值并非相对于目的符号的地址，因为压根不知道符号地址在哪里） 修改之后的“相对地址”即为”重定位后的值“ 想要求这个值，需要考虑将来执行call指令的时候，当执行call指令的时候，PC已经到了call指令对应地址的+5位置（或者是“重定位的值”的+4位置） 然后跳转到目的地址（S：重定位符号的地址） 在这里：S= P（重定位的值的地址）+4 （因为重定位的值的地址再+4就是此时PC的值）+重定位的值 因此：重定位的值=S+A-P.其中S表示Symbol（符号的地址），A表示Addend（修正值），P表示Postion（重定位的位置的地址）

R_386_32的重定位

变量符号对应32

在32位，往往变量用绝对地址，函数用偏移地址 重定位的值=S+A，（A和PC32的重定向格式是相同的，都是重定位地址的值，通常为0）
